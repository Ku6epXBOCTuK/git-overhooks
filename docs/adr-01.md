# ADR-01: Архитектура git-overhooks

**Статус:** Принят, частично заменен на ADR-02
**Заметка:** Логика команды `git-overhooks install` была изменена в ADR-02.

---

## Контекст

Разрабатывается инструмент `git-overhooks` для управления Git-хуками. Требования:

- Запуск хуков из нескольких источников в строгом порядке: глобальные, локальные неверсионируемые, локальные версионируемые, Husky, оригинальные хуки (лежащие в `.git/hooks`).
- Кроссплатформенность (Windows, Linux, macOS).
- Простая установка без необходимости править каждый репозиторий вручную.
- Не ломать существующие хуки, не требовать миграции.
- Все директории, создаваемые инструментом, должны иметь имя `.git-overhooks` (в соответствии с названием приложения).

## Ограничение

Приложение не может отслеживать изменение `core.hooksPath` в реальном времени. Если другой инструмент или пользователь изменят этот параметр, глобальные хуки перестанут работать. Для восстановления необходимо повторно выполнить `git-overhooks install --force`. В будущем может быть добавлена команда `git-overhooks check` для диагностики.

---

## Решение

### 1. Глобальная установка через `core.hooksPath`

При установке (`git-overhooks install`) выполняются следующие действия:

- Создаётся директория `~/.git-overhooks` (глобальная для пользователя).
- Для **каждого стандартного хука Git** (список предопределён) создаётся поддиректория `~/.git-overhooks/<hook>.d/`. Это делается автоматически, чтобы пользователь сразу мог складывать туда свои глобальные скрипты.
- Внутри `~/.git-overhooks` для каждого стандартного хука создаётся файл-обёртка с именем хука (например, `pre-commit`) **без расширения**.  
  Содержимое обёртки:

  ```bash
  #!/bin/sh
  exec /абсолютный/путь/к/git-overhooks hook <hook-name> "$@"
  ```

  На Windows этот файл также создаётся без расширения, с shebang, и будет обрабатываться Git для Windows через его встроенный `sh`.

- **Выполняется поиск интерпретатора `sh` на Windows** (см. раздел 4). Найденный путь сохраняется в конфигурационный файл для дальнейшего использования.
- Выполняется команда:

  ```bash
  git config --global core.hooksPath ~/.git-overhooks
  ```

  Если параметр уже задан, выводится предупреждение. Для перезаписи требуется флаг `--force`. Старое значение сохраняется в конфигурационном файле (см. раздел 5) для возможности восстановления при удалении.

После этого **все** Git-репозитории пользователя будут использовать хуки только из этой директории. Локальные хуки в `.git/hooks` каждого репозитория **остаются нетронутыми**, но Git их игнорирует.

### 2. Терминология для типов хуков

Чтобы избежать путаницы, вводим следующие названия для различных уровней:

- **Глобальные (global)** – хуки, лежащие в `~/.git-overhooks/<hook>.d/`. Действуют для всех репозиториев пользователя.
- **Локальные для рабочей копии (local)** – неверсионируемые хуки, хранящиеся в `.git/.git-overhooks/<hook>.d/`. Специфичны для конкретного экземпляра репозитория (не распространяются через git).
- **Локальные для проекта (project)** – версионируемые хуки, хранящиеся в корне репозитория: `.git-overhooks/<hook>.d/`. Они могут быть добавлены в репозиторий и использованы всеми участниками.
- **Husky** – хуки из `.husky/<hook>` или `.husky/_/<hook>`.
- **Оригинальные (original)** – хуки, которые лежат в `.git/hooks/<hook>` и были там до установки `git-overhooks`. Они выполняются в последнюю очередь.

Эти термины будут использоваться в документации и сообщениях пользователю.

### 3. Работа при срабатывании хука

Когда пользователь выполняет действие, вызывающее хук (например, `git commit`), Git запускает обёртку `~/.git-overhooks/pre-commit`. Обёртка вызывает `git-overhooks hook pre-commit` с аргументами, переданными Git.

Приложение `git-overhooks` в режиме `hook`:

- Определяет корень текущего репозитория (`git rev-parse --show-toplevel`).
- Определяет директорию Git (`git rev-parse --git-dir`), чтобы знать, где лежит `.git/hooks`.
- Формирует список источников скриптов в следующем порядке:
  1. **Глобальные** – все файлы из `~/.git-overhooks/<hook>.d/` (сортируются по имени).
  2. **Локальные для рабочей копии** – файлы из `$GIT_DIR/.git-overhooks/<hook>.d/`.
  3. **Локальные для проекта** – файлы из `$REPO_ROOT/.git-overhooks/<hook>.d/`.
  4. **Husky** – если существует файл `.husky/<hook>` или `.husky/_/<hook>`, он добавляется как отдельный скрипт.
  5. **Оригинальные** – файл `$GIT_DIR/hooks/<hook>` (если он существует и не является обёрткой от другого инструмента). Этот файл выполняется как есть.
- Все собранные скрипты выполняются **последовательно** в порядке списка. Каждому скрипту передаются те же аргументы, которые приложение получило от Git.
- Если какой-либо скрипт завершается с ненулевым кодом, выполнение немедленно прекращается и этот код возвращается Git'у. Если все скрипты успешны, возвращается 0.

Внутри каждой директории файлы выполняются в **алфавитном порядке**. Пользователь может управлять порядком, используя цифровые префиксы в именах файлов (например, `10_setup.sh`, `20_test.sh`).

**Обработка символических ссылок:** В оригинальных хуках могут встречаться символические ссылки. В текущей версии они не обрабатываются специально – ОС сама разрешает ссылку при запуске, что обычно работает корректно. В будущих версиях может быть добавлена явная поддержка (например, переход по ссылке или проверка на зацикливание).

### 4. Поиск `sh` на Windows

При установке (`git-overhooks install`) выполняется поиск интерпретатора `sh.exe`, необходимого для запуска скриптов без расширения (включая shebang-файлы). Алгоритм:

1. Проверяется наличие `sh.exe` в `PATH` (на случай, если пользователь выбрал соответствующую опцию при установке Git).
2. Если не найден, ищется `git.exe` в `PATH` (он обязан быть, иначе Git не работает). По пути к `git.exe` восстанавливается корень установки Git (обычно `...\Git\cmd\git.exe` → подняться на два уровня → `...\Git\usr\bin\sh.exe`).
3. Если и это не дало результата, проверяются стандартные пути установки: `C:\Program Files\Git\usr\bin\sh.exe`, `C:\Program Files (x86)\Git\usr\bin\sh.exe`.
4. Найденный путь сохраняется в конфигурационном файле (см. раздел 5) для использования при последующих запусках хуков.

Если `sh` не найден, установка прерывается с понятным сообщением, предлагающим пользователю установить Git для Windows или указать путь вручную через флаг `--sh-path`.

### 5. Конфигурация

Все настройки хранятся в едином конфигурационном файле: `~/.git-overhooks/config.toml`. Это позволяет держать все данные приложения в одной папке.

Пример содержимого:

```toml
# Путь к интерпретатору sh на Windows (сохраняется после установки)
sh_path = "C:\\Program Files\\Git\\usr\\bin\\sh.exe"

# Предыдущее значение core.hooksPath (если было перезаписано)
previous_hooks_path = "/home/user/old-hooks"

# Другие настройки могут добавляться позже (например, игнорируемые паттерны)
```

### 6. Команды CLI

- `git-overhooks install [--force] [--sh-path <path>]` – выполняет глобальную установку:
  - Создаёт `~/.git-overhooks` и поддиректории `.d` для всех хуков.
  - Создаёт обёртки.
  - Ищет `sh` на Windows (если не указан `--sh-path`) и сохраняет путь в конфиг.
  - Устанавливает `core.hooksPath` глобально. Если параметр уже существует, без `--force` выдаёт предупреждение и не меняет; с `--force` перезаписывает, сохраняя старое значение в конфиг.
- `git-overhooks uninstall [--remove-files]` – удаляет глобальную настройку:
  - Возвращает `core.hooksPath` к предыдущему значению (если оно сохранено в конфиге) или удаляет параметр.
  - С флагом `--remove-files` удаляет `~/.git-overhooks`.
- `git-overhooks init-repo` – создаёт локальную структуру в текущем репозитории:
  - Создаёт директорию `.git-overhooks/` в корне репозитория (для версионируемых хуков).
  - Создаёт директорию `.git/.git-overhooks/` (для неверсионируемых хуков).
  - Для каждого стандартного хука создаёт пустые поддиректории `.d` внутри обеих папок (опционально, можно добавить флаг `--create-dirs`).
- `git-overhooks run <hook> [args...]` – ручной запуск хука для тестирования (без участия Git). Полезно для отладки.
- `git-overhooks hook <hook> [args...]` – внутренняя команда, вызываемая обёртками; может быть скрыта из справки.
- `git-overhooks fix-perms [<path>]` – рекурсивно устанавливает права на выполнение для файлов в указанной директории (Unix). По умолчанию работает с `~/.git-overhooks`. На Windows выдаёт подсказку, что права не требуются.

### 7. Обработка ошибок и подсказки

- Если при запуске хука встречается файл, который не является исполняемым на Unix, выводится предупреждение с предложением использовать `git-overhooks fix-perms`.
- Если файл не удаётся запустить по другим причинам (например, бинарник не найден), выводится диагностика и хук прерывается с ошибкой.
- На Windows для неисполняемых файлов (без расширения) используется `sh`, поэтому предупреждения о правах не требуется.

## Последствия

### Положительные

- Единая точка управления для всех репозиториев.
- Не требуется миграция существующих хуков – они остаются на месте и выполняются.
- Автоматическое создание глобальных .d-директорий упрощает начало работы.
- Понятная терминология для разных уровней.
- Конфигурация собрана в одной папке.
- Кроссплатформенность обеспечена (поиск `sh` на Windows, корректный запуск скриптов).

### Отрицательные / риски

- Конфликт с существующим `core.hooksPath` решается через `--force` и сохранение старого значения, но пользователь должен быть внимателен.
- На Windows требуется поиск `sh`, что добавляет сложность, но решается однократно при установке.
- Символические ссылки в оригинальных хуках пока не обрабатываются специально (но это редкость и обычно работает).

## Roadmap

### Этап 1: MVP

- Реализация команд `install`, `uninstall`, `hook`, `init-repo`, `run`.
- Поддержка источников: глобальные, локальные для рабочей копии, локальные для проекта, оригинальные.
- Поддержка Unix (Linux, macOS) полностью.
- Поддержка Windows с поиском `sh` и корректным запуском скриптов (через `sh` для файлов без расширения).
- Сборка бинарников через GitHub Actions для трёх платформ.
- Базовая документация в README.

### Этап 2: Интеграция с Husky

- Добавление обнаружения хуков Husky (современный `.husky/<hook>` и устаревший `.husky/_/<hook>`).
- Включение их в порядок выполнения (после локальных, до оригиналов).
- Тестирование совместимости с разными версиями Husky.

### Этап 3: Улучшение установки и конфигурации

- Команда `fix-perms` для Unix (установка прав на выполнение).
- Сохранение предыдущего значения `core.hooksPath` в конфиг и восстановление при `uninstall`.
- Конфигурационный файл `~/.git-overhooks/config.toml` с возможностью ручного редактирования.
- Возможность указать путь к `sh` вручную через флаг `--sh-path` при установке.

### Этап 4: Дополнительные возможности

- **Поддержка pre-commit** – если в репозитории есть `.pre-commit-config.yaml`, можно добавить вызов `pre-commit run` как один из источников (опционально).
- **Игнорирование скриптов** – через конфигурационный файл можно будет указывать паттерны для пропуска определённых файлов (например, `*.bak`).
- **Миграция существующих хуков** – если при установке с `--force` был перезаписан `core.hooksPath`, можно предложить команду для переноса хуков из старой директории в новую структуру (например, `git-overhooks migrate <old-path>`).

### Этап 5: Распространение и экосистема

- Автоматическая публикация релизов на GitHub с приложением бинарников.
- Добавление формул для Homebrew (macOS) и манифестов для Scoop (Windows).
- Написание подробной документации, включая примеры использования для разных сценариев (глобальные линтеры, хуки для команды и т.д.).
- Создание веб-сайта или страницы с документацией (опционально).

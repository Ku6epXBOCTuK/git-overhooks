# План: упрощение проекта и переименование в goh

**Статус:** план, реализация pending

## Контекст

Текущая реализация имеет высокую когнитивную сложность: непонятно как начать пользоваться,
лишние шаги при установке, отсутствует полезное поведение «из коробки». Проект переименовывается
в **goh** (git overhooks), конфигурация переезжает в `~/.config/goh`.

Принятые решения (обсуждены):

- Механизм перехвата — **`core.hooksPath`** (не shim git.exe в PATH, не git alias).
- Порядок локальных хуков — **global → husky → .git-hooks → родные .git/hooks**.
- Форматтер перед коммитом — **отдельный скрипт**, который `goh install` кладёт в глобальные хуки
  (не зашитая в бинарь логика).

---

## 1. Переименование и структура

- Бинарь: `git-overhooks` → **`goh`**.
  - `Cargo.toml`: `name = "goh"` (имя пакета можно оставить `git-overhooks` или тоже переименовать —
    решить при реализации; для `cargo install` важен `[[bin]] name = "goh"`).
  - `clap` `name = "goh"` в `Cli`.
- Домашняя папка приложения: `~/.git-overhooks` → **`~/.config/goh`**
  (использовать `dirs::config_dir()`, на Windows это `%APPDATA%\goh`, на Linux/macOS `~/.config/goh`).
- Внутренняя структура **сохраняется**:

  ```
  ~/.config/goh/
  ├── bin/           # файлы-обёртки хуков (то, что подставляется в core.hooksPath)
  ├── hooks.d/       # глобальные пользовательские хуки
  │   └── <hook>.d/  # по директории на каждый стандартный хук
  └── config.toml    # опционально, позже
  ```

- `hook.template` обновить: комментарии и путь упоминать goh.

## 2. justfile: команда install

Новая команда `install` в justfile (старую `install` с `cargo run` заменить/переименовать в `dev`):

- Шаг 1: `cargo install --path .` — ставит бинарь глобально (~/.cargo/bin), чтобы `goh` был доступен
  везде.
- Шаг 2: запуск `goh install` (именно установленный бинарь, не `cargo run`).

## 3. Механизм перехвата: core.hooksPath

Рассмотренные варианты:

1. **core.hooksPath (выбран).** Git сам вызывает наши обёртки из `~/.config/goh/bin`.
   Плюсы: официальный механизм, работает для всех репозиториев пользователя, не трогает PATH,
   легко откатить (`git config --global --unset core.hooksPath`), не ломает GUI-клиенты.
   Минус: перехватываются только хуки, а не сам git — для задач проекта этого достаточно.
2. Shim `git.exe` раньше настоящего в PATH — отклонено: хрупко (порядок PATH), ломает GUI/инструменты,
   сложно диагностировать.
3. Git alias (`git config --global alias.commit '!goh ...'`) — отклонено: не работает в GUI, скриптах
   и инструментах.

Значит `goh install` = «заменить вызов оригинального git» лишь в части хуков:
`git config --global core.hooksPath <путь к ~/.config/goh/bin>`.

## 4. Порядок выполнения хуков

При срабатывании хука (например `git commit` → обёртка → `goh hook pre-commit "$@"`) скрипты
выполняются последовательно из источников в порядке:

1. **Глобальные**: `~/.config/goh/hooks.d/<hook>.d/*` (алфавитный порядок).
2. **Husky**: `.husky/<hook>` или `.husky/_/<hook>` (относительно корня репозитория).
3. **`.git-hooks`**: `.git-hooks/<hook>` (версионируемые хуки проекта).
4. **Родные**: `.git/hooks/<hook>` (оригинальные хуки репозитория).

Правила:

- Каждый источник выполняется, только если файл/файлы существуют.
- Каждому скрипту передаются аргументы, полученные от Git.
- Ненулевой код выхода любого скрипта → немедленная остановка, код возвращается Git'у.
- Новая подкоманда: `goh hook <hook-name> [args...]` (внутренняя, вызывается обёртками).
- Обёртки в `bin/` создаются для всех стандартных хуков (список GIT_HOOKS остаётся).

## 5. Глобальный pre-commit: автоформатирование

`goh install` дополнительно создаёт скрипт (например
`~/.config/goh/hooks.d/pre-commit.d/00-format.sh`), если его ещё нет (не перезаписывать
существующий/изменённый пользователем).

Поведение скрипта при `pre-commit` (в корне репозитория):

1. **Node.js**: если есть `package.json` и в нём есть скрипт `format`:
   - определить пакетный менеджер по lock-файлам:
     `pnpm-lock.yaml` → `pnpm format`; `yarn.lock` → `yarn format`;
     `bun.lockb`/`bun.lock` → `bun run format`; иначе → `npm run format`.
   - перед запуском зафиксировать список unstaged-изменений (`git diff` без `--cached`),
     после форматтера сравнить: если изменения появились/изменились — **остановить коммит** с
     ненулевым кодом и сообщением вида «форматирование было применено, проверьте unstaged изменения
     и закоммитьте их».
   - если скрипта `format` в `package.json` нет — пропустить.
2. **Rust**: если есть `Cargo.toml` — запустить `cargo fmt`. Аналогично: появились unstaged-изменения →
   остановить с сообщением.
3. Если ни один форматтер не применился — выйти с 0, коммит продолжается.

Детали:

- Форматтеры Node и Rust независимы: проект может иметь оба.
- Проверка «есть ли изменения» — по unstaged (`git diff`), а не staged: форматтер правит файлы в
  рабочей копии, изменённая часть и есть то, что пользователь должен просмотреть и добавить.
- Один и тот же скрипт работает на Windows (Git для Windows sh) и Unix — только POSIX sh.
- `--force` в `goh install` может перезаписать скрипт свежей версией (перезапись шаблонов).

## 6. Что выкидывается / упрощается

- Убрать копирование самого себя (`copy_self`) — бинарь уже установлен глобально через `cargo install`,
  обёртки ссылаются прямо на путь из `current_exe()` (или из `which goh`).
- Убрать интерактивный `confirm` в конце install (мёртвый код: обе ветки делают одно и то же).
- Логику проверки/перезаписи `core.hooksPath` по ADR-02 сохранить, упростив: если текущее значение
  не наше — предупредить, перезапись только с `--force`.
- `config.rs` пока не используется — не трогать/удалить при реализации.

## 7. Задачи реализации (чек-лист)

1. Переименовать бинарь в `goh` (Cargo.toml, clap), папку в `~/.config/goh` (`dirs::config_dir()`).
2. justfile: `install` = `cargo install --path .` + `goh install`; старую команду переименовать в `dev`.
3. Команда `goh hook <hook> [args...]` + последовательный запуск источников
   global → husky → .git-hooks → .git/hooks.
4. Генерация скрипта автоформатирования в `hooks.d/pre-commit.d/00-format.sh` при install.
5. Пометить ADR-01/ADR-02 как устаревшие (заменены этим планом).
6. Проверить на тестовом репозитории: husky, .git-hooks, родные хуки, npm/pnpm/cargo форматтер.

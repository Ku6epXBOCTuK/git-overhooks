# Backlog

## WIN-001: format-скрипт зависит от GNU-утилит (grep/cmp/mktemp)

**Статус:** открыто, отложено

**Где:** `src/format.template` (и все будущие скрипты в `hooks.d`).

**Проблема:** на Windows `grep`, `cmp`, `mktemp` не входят в системный PATH.
Они есть только внутри Git for Windows (`<git>\usr\bin\`), и Git подмешивает их в PATH
только для процессов хуков.

**Как поведёт себя сейчас:**

- Реальный поток `git commit` → **работает** (проверено): Git добавляет свой `usr/bin` в PATH хука, goh наследует его.
- Ручной запуск `goh hook pre-commit` из терминала → npm-детект (`grep`) может тихо не сработать: `if` короткозамкнётся по ошибке «grep: not found», Node-форматтер пропустится. Rust-ветка не зависит от GNU-тул, пострадает только Node.

**Варианты решения (нужно выбрать):**

1. **Копировать нужные exe к себе** — в `~/.config/goh/bin` (или в отдельную папку) класть `grep.exe`, `cmp.exe`, `mktemp.exe`, ... и в format-скрипте/раннере подключать `PATH` на эту папку. Плюс: самодостаточно, не зависит от расположения Git. Минус: тащим бинарники, лицензии/версии.
2. **Использовать Git'овские утилиты по абсолютному пути** — мы уже умеем находить `sh` рядом с `git` (`<git>\usr\bin\sh.exe`); из того же корня берутся `grep/cmp/mktemp/sed/...` и подкладываются в PATH раннера (`goh hook`) или скрипта. Плюс: ничего копировать не надо. Минус: знаем о расположении Git.
3. **Убрать GNU-зависимость из форматтера** — определять `format` средствами Node (`npm pkg get scripts.format`, npm гарантирован в PATH для node-проектов), заменить `mktemp` на фиксированный временный файл, `cmp` — на сравнение переменных в самом sh (POSIX-встроенное). Плюс: кроссплатформенно начисто. Минус: чуть сложнее скрипт.
4. **Прочее** — например, BUSYBOX-совместимый shim поверх `git` (сложно), утилита `git --exec-path` для libexec-git (там не всё), требовать от пользователя добавить `usr/bin` в PATH (плохой UX), ХРАНИТЬ КАК ЕСТЬ (работает в реальном потоке, но хрупко для ручных запусков).

**Решение проверить:** при первом ручном `goh hook pre-commit` без git-окружения npm-детект не сработает.

## Идеи из архивных ADR (adr-01/adr-02, архивированы)

## FEAT-001: `goh run <hook>` — ручной запуск хука

Запуск хука без участия git, для отладки/проверки скриптов. Источник: adr-01, команды CLI.
Плюс к этому — `goh hook` уже скрыт из справки; `run` будет публичным аналогом.

## FEAT-002: локальные версионируемые хуки проекта

Помимо `.git-hooks/` добавить два уровня из adr-01:

- `.git-overhooks/<hook>.d/` — версионируемые, распространяются участникам (проектные)
- `.git/.git-overhooks/<hook>.d/` — неверсионируемые, для конкретной копии (рабочая копия)

Порядок по adr-01: глобальные → рабочая копия → проектные → husky → `.git-hooks` → оригинальные.
Понадобится `init-repo` (создание структуры) или создание .d-директорий на лету.

## FEAT-003: uninstall восстанавливает предыдущий core.hooksPath

Сейчас `goh uninstall` просто снимает `core.hooksPath`. Сохранять старое значение в
`~/.config/goh/config.toml` при `install --force` (когда перезаписываем чужое) и возвращать
его при uninstall. Источник: adr-01 `--force`, adr-02.

## FEAT-004: `goh check` — диагностика дрейфа core.hooksPath

`core.hooksPath` может сменить другой инструмент/пользователь, и глобальные хуки замолчат.
Команда сверяет текущее значение с нашим `bin/` и сообщает статус (+ hint про `install --force`).
Источник: adr-01, раздел «Ограничение».

## FEAT-005: `goh fix-perms` (Unix)

Рекурсивно выставить exec-бит на скрипты в `~/.config/goh` (и прочих путях). На Windows —
подсказка, что не нужно. Источник: adr-01.

## FEAT-006: Дистрибуция (CI-релизы, Homebrew/Scoop)

GitHub Actions: сборка под Windows/Linux/macOS, авторелизы. Формулы Homebrew и манифест Scoop.
Источник: adr-01, Этап 5.

## FEAT-007: `goh commit [type] [message] [scope]` — как cog commit

Создание conventional commit через goh, интерфейс как у cocogitto (`cog commit`):

- `goh commit docs "meant"` → `docs: whence`;
- `goh commit fix "bug" parser` → `fix(parser): bug`.

Собирает conventional-хедер, дальше вызывает `git commit` (после прогона хуков).
Цель — не зависеть от cocogitto (см. BUG-001).

## BUG-001: cocogitto (cog commit) падает, когда активен goh

**Статус:** исследовано (без углубления в код cog); виновник — cocogitto.
План: открыть issue и сделать PR в cocogitto.

**Симптом (Windows):** при активном goh (`core.hooksPath` указывает на `~/.config/goh/bin`):
`cog commit docs "update docs, add readme and license"` → `Error: IO Error / cause: %1 is not a valid Win32 application. (os error 193)`.

После `goh uninstall` — коммит через cog работает штатно.

**Вывод (обоснование):** ошибка 193 — это `CreateProcess` на файл, который не является
Windows-исполняемым. goh здесь не виноват: механизм `core.hooksPath` + обёртки без расширения
с shebang — стандартный (как у husky/pre-commit), и `git commit` с активным goh работает
(Git for Windows сам раскрывает shebang через свой `sh.exe`). Раз через `git commit` обёртка
запускается штатно, а в коге падает — cog спавнит хук напрямую (CreateProcess без shell),
не проводя shebang-обработки, т.е. баг в cocogitto (или его libgit2-слое), а не в goh.

**План:**

1. Найти в коде cog, где он спавнит хуки (git2/libgit2 vs свой runner), воспроизвести, сделать PR в cocogitto.
2. Пока cog не починен — при желании временный safety switch в goh (флаг/env, обходит хуки для одной команды), не как основное решение.
3. FEAT-007 (`goh commit`) остаётся независимым путём — меньше зависимости от cog.

# goh — Git OverHooks

Управление Git-хуками без страха. Запускает хуки из нескольких источников в строгом порядке
для **всех** репозиториев пользователя, не ломая существующие хуки.

## Идея

Git позволяет задать одну глобальную папку для хуков через `core.hooksPath`.
goh кладёт туда свои обёртки и по срабатыванию хука запускает ваши скрипты по порядку:
**глобальные → Husky → `.git-hooks` → родные `.git/hooks`**.

Все репозитории пользователя получают хуки сразу, без правки каждого вручную.
Существующие хуки (Husky, `.git-hooks`, `.git/hooks`) не мигрируются и не ломаются —
goh просто запускает их по очереди.

После установки в `~/.config/goh/hooks.d/pre-commit.d/00-format.sh` создаётся встроенный
хук автоформатирования: если есть `package.json` со скриптом `format` — запускается
`npm run format` (или `pnpm`/`yarn`/`bun` по lock-файлам); если есть `Cargo.toml` — `cargo fmt`.
Если форматтер изменил файлы — коммит останавливается с просьбой просмотреть изменения.

Рядом создаются `01-comments.sh` — контроль комментариев (см. «Правила комментариев») —
и `02-tests-ascii.sh` — контроль того, что названия тестов и тексты ассертов состоят
только из ASCII-символов (см. «ASCII-контроль тестов»).

## Правила комментариев

`goh comments` проверяет все незакоммиченные файлы (staged, unstaged и untracked)
и находит четыре вида нарушений:

1. комментарий без разрешённого ключевого слова — нарушение, его можно удалить целиком
   (только по явному флагу `--remove`, `--write` никогда не удаляет комментарии);
2. комментарий длиннее `max_lines` строк обрезается, сразу после маркера добавляется
   пометка `[cut]` — на той же строке, поэтому лимит не расходуется;
3. не-ASCII символы в комментарии — нарушение, автоматически не исправляется;
4. `to-do`, `TO-DO`, `ToDo`, `todo` → `TODO`; `fix-me`, `FixMe` → `FIXME`.

Регистр приводится автоматически. Пунктуация учитывается только если она
перечислена алиасом: `to-do` станет `TODO`, а `to.do` будет считаться комментарием
без ключевого слова.

Ключевое слово ищется в первой непустой строке блока. Декорации вокруг него
снимаются, поэтому `**NOTE**: x`, `*NOTE*: x`, `[NOTE]: x`, `- NOTE: x` и `1. NOTE: x`
считаются комментарием с ключевым словом. При `--write` декорации убираются,
остаётся канон: `// **NOTE**: x` → `// NOTE: x`.

Один блок может дать несколько сообщений — на каждое нарушение своя строка отчёта
с одним и тем же `file:line`. Например, блок без ключевого слова, который ещё и
длиннее `max_lines`, отмечается двумя пунктами: «нет ключевого слова» и «слишком
длинный». Исключение: если блок удаляется по `--remove`, в отчёте остаётся только
сообщение об удалении — претензии к удалённому блоку неактуальны.

Не трогаются shebang, директивы (`eslint-disable`, `prettier-ignore`,
`nolint`, `go:generate`, `vim:`) и настоящая документация:

1. `///` и `//!` в Rust — это doc-комментарии по спецификации языка
2. `/** */` в `.js`/`.ts`/`.svelte`/`.vue`/`.astro`, если внутри есть хоть один признак JSDoc:
   - тег (`@param`, `@returns`, `@throws`, `@type`, `@typedef`, `@property`, `@example`,
     `@deprecated`, `@template`, `@see`, `@extends`, `@implements`, `@default`, `@enum`,
     `@private`, `@public`)
   - тип в фигурных скобках (`{string}`, `{Array<T>}`, `{?string}`)
   - ссылка (`{@link X}`, `{@linkcode}`, `{@linkplain}`)
   - markdown (```-блок, `[текст](url)`, http-ссылка)

`/** */` без этих признаков считается обычным комментарием и подпадает под правила —
достаточно одного сигнала, чтобы блок остался нетронутым.

Текст внутри строковых литералов комментарием не считается: raw-строки Rust,
`"""..."""` в Python и TOML, backtick-шаблоны в JavaScript и Go, heredoc в shell,
PHP и Ruby, block-скаляры в YAML, `[[...]]` в Lua.

Исключения задаются ignore-файлами, они объединяются: файл пропускается, если его путь
подошёл под любой источник — служебные каталоги (`.git`, `.svn`, `.hg`, `.bzr`, `.DS_Store`,
`Thumbs.db`, `$RECYCLE.BIN`), `~/.config/goh/.gohignore`, `.gohignore` (корневой и вложенные)
и `.gitignore` (корневой и вложенные, паттерны каждого — относительно своего каталога).

Файлы вложенных репозиториев (каталоги со своим `.git`) не проверяются, и об
этом печатается строка в отчёте.

Без флагов команда только сообщает о нарушениях и ничего не пишет. Исправления
применяются по флагу `--write`; хук `01-comments.sh` запускает команду с `--staged`
и без `--write` — он только проверяет staged-файлы и роняет коммит с отчётом.

`--write` никогда не удаляет комментарии: он только приводит написание ключевого слова
к канону и обрезает длинные блоки. Удаление комментария без ключевого слова — отдельное
явное действие `--remove`, его нужно задавать вместе с `--write`:

```sh
goh comments                   # отчёт по всем незакоммиченным файлам
goh comments --staged          # только staged (то, что уедет в коммит)
goh comments --all             # все файлы репозитория, кроме игнорируемых
goh comments --write           # отчёт + автофикс (сочетается с --staged/--all)
goh comments --write --remove  # автофикс + удаление комментариев без ключевого слова
```

Файлы правит в рабочем дереве и **ничего не добавляет в индекс** — коммит падает,
решение за пользователем.

`--all` проверяет все файлы репозитория, кроме игнорируемых. Каталоги из
ignore-файлов не обходятся, симлинки не разворачиваются, файлы крупнее 1 МБ не
читаются.

Файл с известным расширением, который не читается как UTF-8, — это находка
«битая кодировка» (кириллица, сохранённая в cp1251, и т.п.): он ломает проверку
с сообщением «re-save as UTF-8». Настоящие бинарники распознаются по NUL-байтам
и control-символам (в том числе MPEG-видео, которое тоже носит расширение `.ts`)
и пропускаются молча.

## ASCII-контроль тестов

`goh tests-ascii` проверяет, что названия тестов и тексты ассертов состоят только
из ASCII-символов: не-ASCII строки ломаются при запуске тестов на другой машине
с другой кодировкой. Проверка ничего не переписывает — только репортит и роняет
коммит.

Что проверяется:

1. **Названия тестов в JS/TS** (файлы `js jsx ts tsx mts cts mjs cjs`) — первый
   строковый аргумент `it()`, `test()`, `describe()`, `specify()`, включая цепочки
   модификаторов (`test.skip()`, `describe.concurrent()`), форму `it.each(table)(title)`
   и шаблонную таблицу `` it.each`table`(title) ``. Вызов метода с таким именем не
   считается названием (`z.string().describe("...")`), кроме `test.describe()`.
2. **Имена функций в Rust** (`rs`) — имя функции с атрибутом `#[test]`
   (другие атрибуты между ними допускаются).
3. **Тексты ассертов в JS/TS** — последний чисто строковый аргумент `assert()`
   и `expect()` с любыми методами (`assert(cond, "msg")`, `expect(value, "msg")`).
4. **Тексты ассертов в Rust** — сообщение `assert!`/`assert_eq!`/`assert_ne!`/
   `debug_assert*!` (последний чисто строковый аргумент: у `assert_eq!(x, "значение")`
   строка — значение, а не сообщение, поэтому нужен третий аргумент), а также первый
   литерал `panic!()` и `.expect()`.

Проходит проверку:

- экранированный юникод (`\u0444`, `\u{442}`) — в исходнике он ASCII;
- строки внутри комментариев, вложенных вызовов и значений (не сообщений).

Файл с проверяемым расширением, не читающийся как UTF-8 (битая кодировка,
например cp1251), — находка и ломает коммит. Бинарники (NUL/control-байты —
например, видео MPEG transport stream с тем же расширением `.ts`) молча
пропускаются.

Механика файлов, игноров и вложенных репозиториев та же, что у `goh comments`.
Флаги: `goh tests-ascii` — все незакоммиченные файлы, `--staged` — только staged
(так работает хук), `--all` — весь репозиторий. Отключить проверку можно удалением
`02-tests-ascii.sh` из `~/.config/goh/hooks.d/pre-commit.d/`.

## Конфиг

Поведение задаётся в двух местах: глобальный `~/.config/goh/goh.toml` и проектный
`goh.toml` в корне репозитория. Проектный файл перекрывает глобальный по каждой
настройке отдельно: если в `goh.toml` задан `max_lines`, глобальный `max_lines`
не применяется, а ключевые слова берутся из того файла, где таблица задана последним.

`~/.config/goh/goh.toml` (в `goh.toml` — тот же формат):

```toml
[comments]
max_lines = 3

# Ключ — каноническое написание, автоматически переводится в верхний регистр.
# Значение — варианты с пунктуацией, которые считаются тем же словом.
[comments.keywords]
NOTE = []
TODO = ["to-do"]
FIXME = ["fix-me"]
```

Чтобы добавить своё слово, достаточно дописать строку:

```toml
[comments.keywords]
BUGFIX = ["bug-fix"]
```

Неизвестный ключ или битый TOML — это ошибка: `goh` печатает путь к файлу, номер
строки и останавливается с ненулевым кодом возврата, а не проверяет файлы по
умолчаниям.

### Ignore-файлы

Пути, которые проверять не нужно, задаются отдельным файлом на каждый скоуп:

- `~/.config/goh/.gohignore` — глобальные паттерны;
- `.gohignore` — паттерны проекта.

Формат как в `.gitignore`: один паттерн в строке, `#` — комментарий.

Три уровня исключений:

1. **Служебные каталоги** (`.git`, `.svn`, `.hg`, `.bzr`, `.DS_Store`, `Thumbs.db`,
   `$RECYCLE.BIN`) — игнорируются всегда, отменить нельзя.
2. **Дефолты** (`node_modules`, `target`, `dist`, `.venv`, кэши и прочее) — лежат в
   `~/.config/goh/.gohignore`, который создаёт `goh install`. Файл обычный: удалил строку —
   папка проверяется, добавил строку — папка пропускается.
3. **Ваши файлы** — `.gohignore` проекта (корневой и вложенные, действуют в `--all`-режиме)
   и `.gitignore` добавляются к дефолтам.

Отменить игнор можно строкой с `!` в `.gohignore` (глобальном или проектном):

```sh
!coverage
```

`.gitignore` читается односторонне: его правила «включить обратно» (`!`) не применяются,
они говорят git'у про отслеживаемые файлы, а не про `goh`. Читаются корневой `.gitignore`
и вложенные (паттерны — относительно каталога, где лежит файл). Вложенные `.gohignore` —
тоже проектные правила: их `!` работает, более глубокий файл сильнее корневого. Приоритет:
проектный `.gohignore` → глобальный `.gohignore` → `.gitignore` (корневой и вложенные).

### Игнор репозиториев и проверок

Чужой репозиторий можно исключить из проверок, ничего не добавляя в него: правила
живут в глобальном `~/.config/goh/goh.toml`, а ключ — сам репозиторий, а не файл в нём.

```sh
goh ignore                        # все проверки для текущего репозитория
goh ignore format                 # только автоформаттер
goh ignore --repo "github.com/acme/*"  # вся организация, откуда угодно
goh unignore comments             # вернуть одну проверку
goh ignore --list                 # что уже проигнорировано
```

```toml
[hooks]
disabled = []                     # для всех репозиториев сразу

[hooks.repos]
"github.com/acme/*" = ["*"]
"github.com/legacy/tool" = ["format"]
```

Ключ — `host/owner/name` из `remote.origin.url`: формы `git@host:owner/repo`,
`ssh://` и `https://` приводятся к одному виду, `.git` и пользователь отбрасываются.
Если ремоута нет, ключом становится абсолютный путь к репозиторию. Ключ может быть
глобом: `github.com/acme/*` накрывает все репозитории владельца.

Проверки: `format`, `comments`, `tests-ascii` (алиас `ascii`). Без аргументов
`goh ignore` выключает все три. Игнор действует только на git-хук: `goh comments`
и `goh tests-ascii`, запущенные руками, проверяют как обычно.

С `--project` правило пишется в `goh.toml` проекта и уезжает в git вместе с ним;
по умолчанию в репозиторий ничего не попадает.

## Установка

Требуется: Rust (для сборки) и `just`.

```sh
just install
```

Что произойдёт:

1. `cargo install --path .` — бинарь `goh` становится доступен глобально;
2. `goh install` — создаёт структуру в `~/.config/goh`, обёртки хуков,
   скрипт автоформатирования и настраивает `git config --global core.hooksPath`.

Если `core.hooksPath` уже занят другим инструментом, `goh install` без `--force`
предупредит и не тронет его.

## Отключение

```sh
goh uninstall            # снимает core.hooksPath, файлы остаются
goh uninstall --remove-files  # дополнительно удаляет ~/.config/goh
```

Откатить вручную: `git config --global --unset core.hooksPath`.

## Структура `~/.config/goh`

```txt
~/.config/goh/
├── bin/           # обёртки хуков (сюда указывает core.hooksPath)
├── hooks.d/       # ваши глобальные хуки
│   └── <hook>.d/  # по папке на каждый стандартный хук:
│       ├── 00-format.sh       # встроенный автоформаттер (pre-commit.d)
│       ├── 01-comments.sh     # контроль комментариев (pre-commit.d)
│       └── 02-tests-ascii.sh  # ascii-контроль тестов (pre-commit.d)
├── goh.toml       # правила комментариев и игнор репозиториев
└── .gohignore     # глобальные паттерны путей + дефолты (deps, сборка, кэши)
```

## Как добавить свой хук

Сложить исполняемый скрипт (POSIX sh) в папку нужного хука, например:

```sh
~/.config/goh/hooks.d/pre-push.d/publish.sh
```

Файлы в папке выполняются по алфавиту — порядок задаётся цифровыми префиксами
(`10_lint.sh`, `20_test.sh`). Скрипту передаются аргументы от Git.

## Порядок запуска

1. **Глобальные** — `~/.config/goh/hooks.d/<hook>.d/*`
2. **Husky** — `.husky/<hook>` или `.husky/_/<hook>`
3. **`.git-hooks`** — `.git-hooks/<hook>` (версионируемые хуки проекта)
4. **Родные** — `.git/hooks/<hook>`

Любой ненулевой код выхода останавливает цепочку и возвращается Git'у.

Встроенные проверки (`00-format.sh`, `01-comments.sh`, `02-tests-ascii.sh`) не
запускаются, если репозиторий или сама проверка в игноре (см. `goh ignore`). Свои
скрипты и хуки других инструментов goh не пропускает никогда.

## Терминология

- **Глобальные** — хуки пользователя, действуют везде.
- **Husky** — хуки из `.husky/`.
- **`.git-hooks`** — версионируемые хуки проекта (в git).
- **Родные** — хуки, лежащие в `.git/hooks` до установки goh.

## Разработка

```sh
just dev             # cargo run -- install -vvvv (без глобальной установки)
just git-show-hooks  # показать текущий core.hooksPath
```
